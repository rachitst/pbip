# PBIP v1.0.0 release notes

**Status: draft.** The `v1.0.0` tag has not been created; it is created at the final review. The full list of
changes, with pull request numbers, is in [`CHANGELOG.md`](../../CHANGELOG.md).

## In plain language

PBIP (Personal Banking Intelligence Platform) is a practice bank built as a student project to the standards a real,
regulated bank would expect. It uses no real money and only made-up customer data.

**What customers can do**

- Register, sign in securely and see all their accounts and their total balance in one place.
- Send money to saved payees, pay bills, and set up payments that repeat, for example every month.
- Download statements as PDF or CSV files and search their past transactions.
- See where their money goes, a financial health score and a forecast of their balance at the end of the month.
- Apply for a loan, book a fixed deposit and compare insurance products.
- Ask a built-in assistant questions such as "how much did I spend on food last month?". The assistant can only
  read the customer's own information; it cannot move money or see anyone else's data.

**How the bank protects customers**

- Every payment is checked for fraud before it goes through. Suspicious payments are held, and a staff analyst
  reviews them. The analyst sees, in plain words, why the payment looked risky.
- The fraud checks combine fixed rules (for example a large payment to a new payee, or a sign-in from an unusual
  place) with machine-learning models. If the models are unavailable, the rules still run, so nothing is let
  through unchecked.
- Staff must use a second sign-in step (a code from an authenticator app). Customers confirm risky payments with an
  extra code.
- Every important action is recorded in an audit log that shows if anyone has altered it.
- Money is recorded with double-entry bookkeeping, as in a real bank, and a payment that is accidentally sent twice
  is carried out only once.

**What staff can do**

- Fraud analysts work through a queue of held payments and approve or reject them.
- Relationship managers see insights about the customers assigned to them.
- Compliance officers check the audit log and see dashboards of exceptions.
- Administrators unlock accounts and change a short list of approved settings.

**Not in this release**

- The bank has not been deployed to a cloud server or tested at production scale yet. Load tests have been run on a
  developer laptop only.
- Product recommendations use rules, not a trained model.
- Two extra fraud patterns from the test data (structuring payments to stay under limits, and sudden activity on a
  dormant account) are not detected by a dedicated rule yet.

### Upgrade and compatibility notes

- This is the first release, so there is nothing to upgrade from. A new database is created with
  `make migrate` (Alembic, single head).
- The API is versioned under `/api/v1`; the OpenAPI contract is in `docs/api/openapi.json`.
- `FRAUD_SCORER=hybrid` needs trained models in `models/fraud` (`make fraud-model` or `make fraud-champion`);
  without them the API scores with rules only.
- Loan eligibility counts as income only credits that recur in 2 of the last 3 months (ADR-0043). A customer whose
  only credit is an opening deposit, as in the seeded demo data, sees no income and gets no income-based loan offer.
- `make fraud-model` now trains `hybrid-lgbm-iforest-2` (data generator v2.3). A machine whose `models/fraud` still
  holds `-1` fails the one API test that loads the real files until it retrains.
- The Groq router is off unless `LLM_PROVIDER=groq` (the default is `ollama`); the assistant then uses Ollama, and rules when Ollama is down.

### Known limitations and open items

- Deployment and staging-scale verification are open (#198; TASK-078, TASK-079, TASK-102, TASK-103).
- The trained recommendation model for TASK-054 is not part of this release (rules-v1 is used, see the model card).
- Fraud scenarios F7 structuring (#274) and F8 dormancy (#275) exist in the synthetic data but have no dedicated
  rule yet.
- The fraud evaluation uses synthetic data only; its numbers do not predict performance on real transactions.
- `minimatch` advisory in development tooling only, blocked upstream (#232).
- The retrained fraud model `hybrid-lgbm-iforest-2` is not promoted: the champion gate refused it only on latency on
  a loaded machine (TASK-084, #107). The served model stays `hybrid-lgbm-iforest-1`.
- Open defects from the bug bash: forecast seasonality (#384), fragile calibration with few positives (#396), the
  dormant `phone_enc` write path (#398), at-rest evidence on the host (#399) and a flaky concurrency test (#403).
- Celery worker metrics are not yet checked against a live Prometheus (#378).
