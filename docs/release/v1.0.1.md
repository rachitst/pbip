# PBIP v1.0.1 release notes

Tagged `v1.0.1` on 4 November 2026 from `main`; the tagged commit and its checks are listed on the
[GitHub release](https://github.com/rachitst/pbip/releases/tag/v1.0.1). This is a patch release on top of
[v1.0.0](v1.0.0.md). The full list of changes, with pull request numbers, is in
[`CHANGELOG.md`](../../CHANGELOG.md).

## In plain language

- **A fraud-rule fix.** The rule that watches long-dormant accounts could be one day short, or tell an analyst an
  account "became active again -1 days ago", when the database's clock ran slightly ahead of the application's. Both
  now read the same clock. No fraud decision changed in our evaluation: the four false-alarm bars and the
  behaviour-regression suite give identical results before and after.
- **The served fraud model can be installed anywhere, exactly.** The promoted model `hybrid-lgbm-iforest-3` is
  attached to the v1.0.0 release as a checksummed bundle. `make fraud-model-release` downloads it and refuses it
  unless every byte matches the pinned checksum. No re-training and no manual copying.
- **Product recommendations can be ordered by a trained model, on simulated data.** We built a simulation of how
  customers take up products, driven by their behaviour (income stability, savings, spending mix, age band, what
  they already hold and what they clicked) plus noise, and not by our own rules. A logistic regression trained on
  it beat the hand-written rules on months it had never seen, so it re-orders the products the rules allow when its
  model file is installed. **These results come from a simulation, not from real customers,** and every response it
  orders says so. The rules still decide which products are eligible and give the reasons.
- **Faster pages.** Repeat visits to the recommendations page and the balance forecast reuse work that has not
  changed. A cached value is never older than the data behind it and is never shown to another customer.
- **A recorded fallback demo.** A script drives the real web app through the demo story and records it in HD. The
  video is attached to this release.

### Upgrade and compatibility notes

- No database migration (the head stays `0029`) and no breaking API change. The OpenAPI contract gains documented
  401/403/429/400 and route-specific 404/409/423 responses (#450); descriptions name `sim-propensity-v2`.
- `docker-compose.yml` mounts `./models/recommendations` read-only into the API and sets `RECOMMENDATION_MODEL_DIR`.
  Without a promoted model there, rules-v1 serves, as before. `make recommendation-model` trains and gates it.
- To serve the exact v1.0.0 fraud model on a new machine: `make fraud-model-release`, then restart the API.

### Verification

- Every change merged with all required checks green (CI Gate: API unit, integration and security tests with
  coverage 96%+, E2E, web, ML, security, Docker images, workflow lint; plus CodeQL).
- Fraud: the evaluation report is byte-identical before and after #447 (new-payee REVIEW 0.28% / 0.43%, STEP_UP
  7.61% / 8.02%, all-legitimate REVIEW 0.040% / 0.059%, recall at REVIEW 0.923), and the TASK-080 behaviour suite
  passes 7 of 7.
- Recommendations: `make recommendation-model` on `main` reproduces the gate exactly (NDCG@3 0.721 vs rules-v1
  0.499, hit-rate@3 0.873 vs 0.741, all six checks pass).
- Fraud bundle: packing twice gives identical bytes, and installing from the release URL gives files identical to the
  served directory.
- Benchmarks on the 2-CPU laptop at load below 4: structuring scoring p95 45.1 ms and mule scoring p95 29.2 ms
  (budget 100 ms); COPY load median 8.69 s (budget 15 s); repeat recommendations p95 26-36 ms (budget 40 ms).
- The full `make check` on the tagged commit, the live demo run on the rebuilt stack and the recorded fallback video
  are listed on the GitHub release page.

### Known limitations and open items

- **TASK-054 criterion 4 (< 40 ms):** met for repeat requests. Not met for the first request after a posting
  under load on the 2-CPU laptop. Its floor is the per-request authentication and session cost every endpoint pays
  (#343, `docs/ml/recommendation-propensity-decision.md`).
- **TASK-055 criterion 3 (< 15 ms):** met for batches of 1-10 events. 100-event batches take about 19 ms, and the
  insert is still synchronous; making it asynchronous needs an owner decision (#78).
- **Analytics < 50 ms under concurrency (#175):** met sequentially, and at 50 virtual users only on the faster CI
  runner class. The floor is documented in `docs/testing/analytics-latency-2026-11-04.md`.
- **The ranker's evidence is simulated.** It is no claim about real customers. 27% of simulated uptakes are of
  products the rules would not offer, and those are not evaluated.
- **Still needing a real server:** staging (#198), at-rest evidence on the host (#399, #145), 500 virtual users
  (TASK-078, #101), staging page-load budgets (TASK-102, #185) and a week of availability data (TASK-103, #186).
- Three moderate npm advisories in dev tooling are blocked upstream (#232).
