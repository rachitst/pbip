# PBIP v1.1.1 release notes

Tagged `v1.1.1` on 8 November 2026 from `main`; the tagged commit and its checks are listed on the
[GitHub release](https://github.com/rachitst/pbip/releases/tag/v1.1.1). The full list of changes is in
[`CHANGELOG.md`](../../CHANGELOG.md), and the staging measurements are in
[performance 2026-11-08](../testing/performance-2026-11-08-oci.md).

## In plain language

v1.1.1 is the first release built for, and tested on, the staging server: a small Arm computer in Oracle Cloud's
free tier at `https://pbip.duckdns.org`.

- **It deploys.** The first deployment found that two background services were reported as unhealthy, which would
  have stopped every release; they are now checked correctly.
- **It no longer seizes up under heavy load.** With 200 or more people using it at once, the old version stopped
  answering for 30 seconds at a time; now it slows down instead, answers everyone, and keeps every balance correct.
- **The assistant answers faster.** Simple "how am I doing with my money?" questions are answered straight away,
  and when the AI service is slow the assistant stops waiting after 2.5 seconds and answers anyway.
- **Behind the scenes:** the staging server is backed up every night to separate storage (and a restore from that
  copy was tested), its availability is checked every 30 seconds, and the monitoring dashboards can watch it.

Nothing changes for customers' data, money movement or fraud decisions. Staging holds no demo data: customers
register themselves, and the demo runs on the local stack.

## Upgrade notes

- No database migration (the schema stays at `0031`).
- A request that waits longer than `DB_POOL_TIMEOUT_SECONDS` (default 30 s) for a database slot now gets
  `503 service_busy` with `Retry-After: 1` instead of a 500 (ADR-0060).
- `GROQ_TIMEOUT_SECONDS` now defaults to 2.5 s and is a wall-clock deadline (bounds 0.5 to 10); a Groq timeout goes
  straight to the keyword rules instead of trying Ollama (ADR-0037 addendum).
- The monitoring stack for staging is optional and started with `bash deploy.sh monitoring` after adding
  `GRAFANA_ADMIN_PASSWORD` and `POSTGRES_MONITOR_PASSWORD` to the host `.env` (ADR-0059, runbook section 1.5).
