# PBIP v1.0.2 release notes

Tagged `v1.0.2` on 4 November 2026 from `main`; the tagged commit and its checks are listed on the
[GitHub release](https://github.com/rachitst/pbip/releases/tag/v1.0.2). This is a patch release on top of
[v1.0.1](v1.0.1.md). The full list of changes is in [`CHANGELOG.md`](../../CHANGELOG.md).

## In plain language

- **Clickstream batches are smaller, so every request stays fast.** The app records page visits and a few
  interactions in batches. A batch may now hold at most 25 events (it was 100), which keeps each request under the
  15 ms target. The web app already sent at most 25, so nothing changes for customers.
- **Why the insert is still synchronous.** We measured an asynchronous design that answers before the events are
  saved. The only version that was fast enough relies on Redis keeping data safe through a crash, which PBIP's
  Redis is not set up or backed up to do. Losing events was not acceptable, so the events are still written to
  the database before the app answers ([ADR-0055](../adr/0055-clickstream-batch-cap-instead-of-asynchronous-insert.md)).
- **Two decisions recorded.** The recommendations page's first-request floor (the sign-in check every page pays)
  is accepted. The token-revocation check stays on every request, because a revoked session must be refused at once
  ([ADR-0021](../adr/0021-access-token-revocation.md), #343).

### Upgrade and compatibility notes

- **API:** stricter validation in v1. A client that sent more than 25 events per batch must split its batches. No
  response field changed. The OpenAPI contract and the web types say `maxItems: 25`.
- **Database:** no migration (the head stays `0029`).

### Measured (GitHub-hosted 4 vCPU runner, through nginx TLS)

| Batch size | p50 | p95 | p99 |
|---|---|---|---|
| 1 event | 7.66 ms | 9.08 ms | 10.87 ms |
| 10 events | 8.04 ms | 9.42 ms | 10.41 ms |
| 25 events | 9.88 ms | 11.57 ms | 13.21 ms |
| k6, 500 events/s in batches of 25 | 9.31 ms | 11.44 ms | 13.72 ms |

The k6 run had 0 failed requests and 0 dropped batches. Batches of 100 under the same load had a p95 of 18.7-20.6 ms.
`docs/testing/events-latency-2026-11-04.md` has every run.
